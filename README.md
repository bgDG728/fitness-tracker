# 健身飲食訓練系統

不只是紀錄工具,是會依照你的表現主動給建議的健身/飲食追蹤系統。用 Streamlit +
SQLite 打造。預設單機本地執行,個人健康資料不會上傳到任何地方;也可以選擇性
接上 Turso(見下方「線上使用」)部署到雲端,手機隨時記錄。

## 功能

**個人設定**
- 身高/體重/年齡/性別/活動量/目標,用 Mifflin-St Jeor 公式算 BMR、TDEE
- 依目標(減脂/維持/增肌)自動算出每日熱量與三大營養素目標

**今日總覽(首頁)**
- 今日熱量/營養素 vs 目標、今日訓練量
- **本週摘要**:過去 7 天記錄天數、平均熱量、週訓練量、體重變化、連續記錄天數

**飲食紀錄**
- **拍照辨識食物**:上傳或拍照,用開源 Chinese-CLIP 零樣本分類自動比對出最
  相近的候選食品(Top 3),使用者從候選中確認選擇——辨識僅供輔助,不會直接
  盲目帶入。份量刻意不做影像估重(見下方說明),預設用 100g 當計算基礎,
  自行調整成實際重量
- **同一張照片有多個食物時,框選單一食物再辨識**:照片上會有一個可拖曳/縮放
  的裁切框(`streamlit-cropper`),使用者自己把框圈住其中一個食物範圍,按
  「辨識這一框」——只對框選的區域算 embedding、比對候選,沿用同一套零樣本
  分類邏輯,不是另外接自動物件偵測模型(那類模型在本機 CPU 會慢很多,切出來
  的框也未必剛好對齊一份食物,容易變成半套功能)。確認加入紀錄後,同一張
  照片可以再把框移到下一個食物繼續辨識,不用重新拍照或上傳
- **食物資料庫搜尋**(衛福部食藥署「台灣地區食品營養成分資料庫」,本機查詢、
  完全免費、不需要任何帳號或金鑰):輸入食物名稱自動帶出每 100g 熱量/營養素,
  填份量(g)自動換算,不用自己查營養標示、不用自己算。原本用 Open Food
  Facts,但那是歐美為主的包裝食品條碼資料庫,查台灣家常菜/在地食材常常查不到
  或抓到不相關的西式包裝食品;改成官方逐年化驗的台灣資料庫後準確度好很多,
  且查詢不需要網路(`import_tfda.py` 已一次性匯入 `fitness.db` 的
  `tfda_foods` 表)
- **西式食物補充**(USDA FoodData Central,美國農業部官方資料庫,同樣免費、
  不需要付費):TFDA 資料庫涵蓋台灣家常菜很完整,但吐司、貝果、優格、起司、
  鮮奶油等西式早餐/輕食幾乎查不到。`import_usda.py` 用固定的一份清單
  (不是整包資料庫倒進來,見腳本內註解)向 USDA 免費查詢 API 補進同一個
  `tfda_foods` 表(用 `source` 欄位跟 TFDA 資料分開管理,重跑任一支腳本
  不會互相覆蓋)。腳本本身可以中斷重跑(resumable):用共用的 DEMO_KEY 會有
  速率限制,查到一半被擋下來的話,重跑同一支腳本會自動接著補,不會重複查
  已經匯入的項目;要跳過速率限制可以到
  [USDA API key 申請頁](https://fdc.nal.usda.gov/api-key-signup)免費申請
  個人 key(不需要信用卡),用環境變數 `USDA_API_KEY` 帶入
- **餐別/時間點**:新增一筆時可選早餐/午餐/晚餐/練前餐/練後餐,預設依現在時間猜
  一個(練前餐/練後餐無法用時間判斷,需自行改選)。當日紀錄依餐別分組顯示,
  各組有自己的小計;舊資料(還沒有餐別欄位時建立的紀錄)會歸在「未分類」
- 也可以手動新增餐點(熱量/蛋白質/碳水/脂肪),當日總計 vs 目標即時對比
- **常用品項**:吃過的東西一鍵帶入,不用每次重打
- **飲食建議**:依今天營養素落差主動提示(例如蛋白質不足時建議食物方向、
  熱量過高或過低時提醒),不是只有冷冰冰的數字

**訓練紀錄**
- **動作目錄瀏覽**:32 種常見動作,依部位分類(胸/背/腿/肩/手臂/核心/臀),
  不需要事先知道正確動作名稱,用選的就好;也可以切換「最近使用過」或
  「自訂輸入」新動作
- 記錄動作/組數/次數/重量/器材(固定式機器/自由重量,選填),「重複上一組」
  一鍵新增同重量同次數
- **快速輸入**:貼上自己習慣的簡記語法(例如「上斜胸推\n固定32*2 36
  41*1 45*1.5」),用規則式(regex)解析器轉成結構化紀錄——不接任何
  AI/付費 API,純文字規則判斷,邏輯透明、免費、行為可預期。語法規則見
  `workout_parser.py` 檔頭註解。解析後會先顯示可編輯的預覽表格,確認/
  修正後才真的寫入資料庫,避免語法邊界情況(例如漏打符號)被誤解析後
  直接污染紀錄
- **教練建議**:選動作時,依上次訓練表現用「雙重漸進」(double progression)
  邏輯建議這次的重量與次數區間(並直接帶入表單預設值),附上建議理由
- **訓練目標 + 科學化區間建議**:每個動作可以分開設定訓練目標(最大力量/
  肌肥大/肌耐力),系統會用預估1RM(e1RM)換算出這個目標對應的重量區間、
  次數區間、建議自覺強度(RPE/RIR),並比對這週已做組數 vs 建議週組數
  區間,提示還差多少組或是否已經過量。數據依據見下方「教練建議的邏輯
  說明」
- **姿勢要點 + 示範圖片**:每個動作都有文字化姿勢提醒,常見動作還有示範圖片
  (來自 free-exercise-db,公共領域授權)
- **各動作歷史最佳表現(PR)**:改用預估1RM(e1RM)排序,不是單純比較誰扛得
  最重——用 Epley 公式換算,能反映「換算下來力量最強的那一組」(例如
  90kg x8下換算比 100kg x1下還高)

**進度圖表**
- 體重趨勢、每日熱量攝取趨勢(含目標參考線)、訓練量趨勢、單一動作歷史重量趨勢

## 專案結構

```
fitness_tracker/
├── app.py                今日總覽首頁
├── db.py                 SQLite 資料庫層
├── calc.py                TDEE / 三大營養素計算
├── coach.py               教練建議邏輯(重量建議/姿勢要點/飲食建議/目標區間/e1RM)
├── workout_parser.py      訓練紀錄「快速輸入」規則式解析器
├── food_db.py             食物資料庫查詢(查本機 tfda_foods 表)
├── food_vision.py         拍照辨識食物(Chinese-CLIP 零樣本分類)
├── import_tfda.py         一次性匯入衛福部台灣食品營養成分資料庫
├── import_usda.py         補充匯入 USDA 西式食物(吐司/優格/起司等 TFDA 缺乏的品項)
├── pages/
│   ├── 1_個人設定.py
│   ├── 2_飲食紀錄.py
│   ├── 3_訓練紀錄.py
│   └── 4_進度圖表.py
├── fitness.db             SQLite 資料庫檔(不會被 git 追蹤,個人資料留在本機)
├── tfda_label_embeddings.npz  拍照辨識用的文字 embedding 快取(不會被 git 追蹤)
└── requirements.txt
```

## 使用方式

```
python -m venv venv
venv\Scripts\python.exe -m pip install -r requirements.txt
venv\Scripts\python.exe import_tfda.py
venv\Scripts\python.exe -m streamlit run app.py
```

`import_tfda.py` 只需要在第一次設定時執行一次,會下載並匯入衛福部食品營養
成分資料庫到本機的 `fitness.db`(之後查詢都是本機資料,不用重跑,除非想拿
官方最新公告的資料重新匯入一次)。

打開 http://localhost:8502(或 Streamlit 顯示的網址),先到「個人設定」填一次
基本資料,才能算出熱量目標。之後每天用「飲食紀錄」「訓練紀錄」記錄,首頁跟
「進度圖表」會自動彙整。

拍照辨識食物第一次使用時,會自動下載 Chinese-CLIP 模型(約幾百 MB)到本機,
並花一點時間把食品資料庫的所有名稱算成 embedding 存快取,這一步只會發生一次,
之後拍照辨識只需要算單張照片的 embedding,幾秒內完成。

## 教練建議的邏輯說明

**重量建議**用的是「雙重漸進」,重訓界常見、有實證基礎的簡單漸進超負荷方法:
- 設定次數目標區間(預設 6-10 下)
- 上次在這個重量做到區間上限(10 下)→ 這次加重(大肌群/複合動作 +2.5kg,
  小肌群/單關節動作 +1kg),次數會退回區間下限是正常現象
- 上次沒做到區間下限(6 下)→ 這次維持同重量,先把次數練起來
- 介於中間 → 同重量,目標多做 1 下

這是基於「最近一次該動作的最重那組」表現計算,不是什麼複雜的 AI 模型,邏輯
透明、你可以自己驗證是否合理。

**訓練目標區間建議**用的是預估1RM(e1RM)+ 目標對應的 %1RM 區間,同樣是規則
寫死在 `coach.py` 的 `GOAL_ZONES`,不接 AI/付費 API:

| 目標 | 強度(%1RM) | 次數 | 建議每週組數 | 自覺強度 |
|---|---|---|---|---|
| 最大力量 | 80-100% | 1-6 下 | 2-5 組 | RPE 8-10(0-2 RIR) |
| 肌肥大 | 60-80% | 6-12 下 | 10-20 組 | RPE 7-9(1-3 RIR) |
| 肌耐力 | 40-60% | 12 下以上 | 10-20 組 | RPE 6-8(2-4 RIR) |

數據參考 2026 ACSM 阻力訓練指引、NSCA 訓練建議,以及 Schoenfeld 等人對訓練量
-肌肥大劑量反應關係的統合分析(5-9 組是有效下限,10-20 組是多數受訓者的有效
區間,超過約 25 組沒有額外好處)。**e1RM**(預估單次最大重量)用 Epley 公式
(weight × (1 + reps/30))換算,只採用 12 下以內的組數,因為這個公式在
2-10 下的準確度最好(誤差通常 5% 內),次數太高時誤差會拉大到 15-20%。

每個動作可以分開設定目標(存在 `exercise_goals` 表),沒設定的預設「肌肥大」。
週組數計算的是「選定日期往前 7 天(含當天)」在同一個動作上做了幾組,跟目標
對應的建議週組數區間比對,不夠或超過都會提示。

## 開發踩雷筆記

用 `venv\Scripts\python.exe -m streamlit run app.py` 啟動時,Streamlit 內部
會另外用系統安裝的 Python(而不是 venv 的 python)產生一個子行程實際 serve
網頁。這代表:
- 只關掉/重啟那個 venv 父行程不夠,子行程可能變成孤兒繼續跑舊程式碼
  (改了程式但網頁行為沒變,通常就是這個原因)
- 要確認目前是誰在真正 serve 網頁,查 `Get-NetTCPConnection -LocalPort 8502`
  拿到 PID,再用 `Get-CimInstance Win32_Process -Filter "ProcessId=<PID>"`
  看完整指令,確認清楚後兩個(父+子)一起關掉再重啟

第一次進「飲食紀錄」頁(第一次 import `food_vision.py`)時,Streamlit 的檔案
監控器(用來支援程式改了自動 reload)會去掃 `transformers` 整個模組樹,實測
花了將近一分鐘、主控台會噴一堆 `ModuleNotFoundError: No module named
'torchvision'` 的訊息。這是正常現象不是錯誤(`torchvision` 本來就沒裝,那些
子模組本來就用不到),純粹是掃描開銷,只會發生這一次,之後開關頁面不會重複。

## 隱私

`fitness.db` 已加進 `.gitignore`,不會被推上 GitHub —— 這是你的體重、飲食、
訓練紀錄,屬於個人健康資料。純本機模式下只留在你自己的電腦上;接上 Turso
部署到雲端後,資料會存在你自己申請的 Turso 資料庫裡(不是公開的,需要
auth token 才能存取),原始碼本身仍然不含任何個人資料。

## 線上使用(比照 notebooklm_listening 的部署方式)

部署在 Streamlit Community Cloud,手機/電腦瀏覽器打開網址即可使用。跟英聽
系統不同的地方:這個 app 有資料庫(飲食/訓練紀錄),Streamlit Cloud 免費方案
的檔案系統不持久,單純把 SQLite 檔案放上去的話,重新部署或休眠喚醒會遺失
資料,所以額外接了 [Turso](https://turso.tech)(SQLite 相容的免費雲端資料庫,
libSQL)。

**首次設定(只需要做一次):**

1. 到 [turso.tech](https://turso.tech) 註冊免費帳號,建立一個資料庫,取得
   `TURSO_DATABASE_URL`(格式 `libsql://xxx.turso.io`)和一組 auth token。
2. 本機複製 `.streamlit/secrets.toml.example` 成 `.streamlit/secrets.toml`
   (已在 `.gitignore`,不會進 git),把上面兩個值填進去 —— 這樣本機開發跟
   雲端版會共用同一份資料,不用另外同步。
3. 部署到 Streamlit Community Cloud 時,在該 app 的 Settings → Secrets 貼上
   同樣的兩個值(TOML 格式)。

`db.py` 會自動偵測有沒有設定這兩個值:沒有就退回純本機 sqlite3(不影響
既有的單機用法);有設定就改用 libSQL 的 embedded replica 模式(本機檔案 +
跟 Turso 遠端同步),雲端和手機看到的是同一份資料。

免費方案的 app 閒置一段時間會「睡著」,重新打開需要等 10-20 秒喚醒,這是
正常現象。**部署後請務必在手機上實際測試過**(記一筆飲食/訓練,重新整理
確認資料還在),不要只憑桌面測試就當作已經完成。
